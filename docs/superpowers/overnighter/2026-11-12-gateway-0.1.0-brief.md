# Overnighter brief: Komogentic 0.1.0, the first version of the gateway

Hi, thank you for taking this one on! We are building Komogentic from an empty repository to a deployable 0.1.0. It is an MCP gateway that lets agents read logs, check status, and deploy or restart stacks in Komodo, each agent strictly with the Komodo account and rights of the person it works for. A small team will use it to let their assistants run their applications. The plan is to review and roll it out tomorrow early afternoon, so a working, honest 0.1.0 matters more than a polished one.

Nobody is available to answer questions during this run. That is intended: the spec has been reviewed by Chris, and everything after it is yours, from the plan to the pull request. The decision rules below tell you how to settle what the spec leaves open.

     `mkdir -p ~/crates && cd ~/crates && curl -sSfL https://static.crates.io/crates/mogh_auth_client/mogh_auth_client-1.7.0.crate | tar xz && curl -sSfL https://static.crates.io/crates/mogh_auth_server/mogh_auth_server-1.8.0.crate | tar xz`
   - Facts already confirmed from these sources:
     - A Komodo API key has no separate id. `CreateApiKeyResponse` is `{ key, secret }`, and `DeleteApiKey { key }` takes the `X-Api-Key` value (`mogh_auth_client` 1.7.0, `src/api/manage.rs:454-511`). The "id stored in the clear" of spec §2 is therefore `key`; that is intended, since `key` alone authenticates nothing without `secret`.
     - `LoginLocalUserResponse` is `JwtOrTwoFactor` (`login.rs:219`). The two-factor branch must end in a clear "two-factor sign-in is not supported" error.
     - `StackListItemInfo` includes `server_name`, and `UpdateListItem` includes `username`, so no extra lookup calls are needed and the closed list of calls holds.
     - 2.x stacks can run in Swarm mode (`swarm_id`/`swarm_name` in `client/core/rs/src/entities/stack.rs:151ff`).
     - Komodo serialises a permission without specifics as a bare string, with specifics as `{ level, specific }`.
   - Record in the report which source each shape came from.

    ```sh
    docker run -d --name komogentic-test-mongo --ulimit nofile=20000:20000 -p 27017:27017 mongo:8 --replSet rs0 --bind_ip_all --wiredTigerEngineConfigString "file_manager=(close_idle_time=5,close_scan_interval=2,close_handle_minimum=250)"
    for i in $(seq 60); do docker exec komogentic-test-mongo mongosh --quiet --eval 'try { rs.status().ok } catch (e) { rs.initiate({_id: "rs0", members: [{_id: 0, host: "127.0.0.1:27017"}]}).ok }' 2>/dev/null | grep -q 1 && break; sleep 1; done
    export KOMOGENTIC_TEST_MONGO="mongodb://localhost:27017/?replicaSet=rs0&directConnection=true" TESTCONTAINERS_RYUK_DISABLED=true
    ```
  - Without Docker, install a MongoDB 8 server in the environment and start it as a single-node replica set the same way.
  - Use MongoDB 8 throughout: compose, CI and tests.
  - Say in the report which way the tests ran.

- **decide:** the green/yellow/red rules in detail, from what Komodo's stack and container states actually are (spec §4 gives the intent).
- **decide:** whether MongoDB needs a replica set (spec §10).
- **decide:** whether `compose.yaml` ships a Traefik variant like Kumbu²'s `compose.traefik.yaml` (spec §7 says "if it fits"): include it, modelled on Kumbu²'s, as an optional file.
- **decide, and this is settled already:** the dashboard session's Komodo JWT is sealed with AES-256-GCM under a key derived from the session cookie's secret, never stored in plain text (pattern: `src/Kumbu.Server/Accounts/Sessions.cs`, where the user key is wrapped under the session).
- **decide, and this is settled already:** a connection whose Komodo key Komodo rejects (401, because the user deleted it in Komodo) goes to the same **needs reconnect** state as in spec §5, with a reason such as `komodo_key_rejected` shown in the dashboard. It can be reconnected through consent like the lost-token case. Deleting a key from the pending-deletion list that Komodo no longer knows counts as done.
- **decide:** stacks in Swarm mode use the same calls; the verdict for them is untested, so say so in the README.
- **decide:** the default wait of `deploy_stack`/`restart_stack`. MCP clients may cut tool calls off well before 10 minutes, so choose a default that fits typical client timeouts (and say which you assumed), return "still running, update id …" when it is reached, and log the choice.

## How to work

- Task by task as in the plan: red test, green, then every mutation individually (break, watch it fail, restore with `git checkout -- <file>`)
- **Subagent-driven** (`superpowers:subagent-driven-development`): one fresh subagent per task, then a spec-compliance review and a code-quality review. Subagents never merge, push or switch branches; you commit and push.
- **Commit and push after every task.** Commit messages are imperative and free-form ("Add the deploy tool"), no Conventional Commits prefix. End each one with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; the commit author is Claude, which is intended.
- **Full verification at the end of each phase:**
  - `dotnet restore --locked-mode && dotnet build --configuration Release --no-restore` (warnings are errors)
  - `dotnet test --solution Komogentic.slnx --configuration Release --no-build`, with `KOMOGENTIC_TEST_MONGO` set as above. `--solution` needs `"test": { "runner": "Microsoft.Testing.Platform" }` in `global.json`, as in Kumbu². Adjust the solution name if you choose another, and use it consistently.
  - `pnpm -C web install --frozen-lockfile && pnpm -C web test --run && pnpm -C web build`
  - Once the Dockerfile exists, `docker build .` if Docker is available
- **Only those commands count as evidence,** plus the CI workflows you write running green on the PR.
- **Repository rules** (they go into this repository's `CLAUDE.md` too, adapted from Kumbu²'s):
  - British English everywhere: code, comments, docs, commit messages, PR description (colour, behaviour, initialise, licence as the noun).
  - Comments only where the reasoning isn't obvious; match the surrounding code's idiom.
  - Source files start with `// SPDX-License-Identifier: AGPL-3.0-or-later` (or the comment form of their language).
  - **Code, tests, examples, configuration and the README name no organisation, customer, employer, person or host.** Use neutral names such as "Anna" and `komogentic.example.org`. Deployment-specific settings go into `.env` or a `compose.override.yaml`. Allowed exceptions:

  - Modern C# (records, pattern matching, minimal APIs); no ORM; MongoDB driver directly.
  - `TreatWarningsAsErrors`, nullable on, `packages.lock.json` per project, restore in locked mode, actions pinned to commit hashes, base images pinned to digests.
  - xUnit v3 for the server, Vitest for the web app. No tests for trivial getters.
  - An `obsidian/` folder as an Obsidian vault (a README in it is enough). Its state files (`obsidian/.obsidian/workspace*.json`, `obsidian/.obsidian/cache`) go into `.gitignore`, its settings don't.

## Deciding without Chris

When the spec leaves something open, or something unforeseen comes up, choose the option that satisfies these, in this order:

1. **Breaks nothing.** Existing behaviour, data and interfaces keep working; prefer the reversible change.
2. **True to the spirit of the application.** Follow its existing patterns, style and architecture, and here especially Kumbu²'s. No new dependencies unless the spec asks for them or Kumbu² already uses them.
3. **Opens no new security hole.** Never weaken authentication, authorisation, validation or secret handling.
4. **True to the spec.**

Where the spec deliberately differs from Kumbu², the spec wins over rule 2. Examples: no user accounts and no Argon2 for passwords, no CI sharding, one image (spec §5 "What is different from Kumbu²", §7).

If a question can only be answered by changing the spec's scope, do not guess: leave that part out and record it in `open-items.md`.

Log every decision you made this way. Put it in the report and in the PR description under **Decisions made without Chris**, each with the options you saw and why you chose this one.
