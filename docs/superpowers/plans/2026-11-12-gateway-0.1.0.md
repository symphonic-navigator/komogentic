# Komogentic 0.1.0 — the gateway — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An MCP gateway that lets agents list, inspect, read logs of, deploy and restart Komodo stacks, each strictly with the Komodo account and rights of the person it works for, reached through OAuth connections (Grok, claude.ai, ChatGPT) or API keys (local agents), managed in a small dashboard.

**Architecture:** One ASP.NET Core minimal-API host (`src/Komogentic.Server`) holding a typed Komodo client with a closed list of calls, MongoDB storage (single-node replica set, transactions as in Kumbu²), Kumbu²'s OAuth authorisation server adapted to seal a per-credential Komodo API secret instead of vault keys, a caller middleware that turns a bearer or cookie into a scoped caller with an authenticated Komodo client, and six MCP tools over stateless Streamable HTTP. A React/Vite/TypeScript dashboard (sign-in, connections and keys, consent) is built into `wwwroot`.

**Tech Stack:** .NET 10, `ModelContextProtocol.AspNetCore` 2.4.0, `MongoDB.Driver` 3.13.0, xUnit v3 on Microsoft.Testing.Platform, Testcontainers.MongoDb, `FakeTimeProvider`; React 18, Vite 6, TypeScript 5, TanStack Query 5, react-router-dom 6, Vitest 2, Testing Library; pnpm 10.32.1, Node 26; Docker multi-stage, Compose, MongoDB 8.

**Spec:** `docs/superpowers/specs/2026-11-12-komogentic-design.md`; brief: `docs/superpowers/overnighter/2026-11-12-gateway-0.1.0-brief.md`. Reference code: Kumbu² at `a991ee02263fa150762ab83e638246ef3427f7f0` (`~/kumbukumbu`), Komodo `v2.3.4` (`~/komodo`), `mogh_auth_client` 1.7.0 and `mogh_auth_server` 1.8.0 (`~/crates`).

## Decisions taken in this plan (logged again in the report)

1. **Replica set: yes.** Token rotation, consent and revocation write several documents that must change together (Kumbu²'s `OAuthTokens` uses transactions); MongoDB transactions need a replica set. Compose initiates `rs0` in its health check, as Kumbu² does.
2. **One server project** (`Komogentic.Server`) with folders `Komodo/`, `Tools/`, `OAuth/`, `Auth/`, `Api/`, `Accounts/`, `Net/`: small enough to stay clear.
3. **Session cookie** `kgt_session`, `Path=/api`, HttpOnly, Secure, SameSite=Strict; the session lives 30 min idle, 12 h at most, and never past the Komodo JWT's `exp` (milliseconds since the epoch in Komodo's `JwtClaims`). The JWT is sealed with AES-256-GCM under `HKDF(secret, "kgt/v1/session-jwt")`.
4. **Verdict** (Komodo `StackState` is snake_case, `StackServiceState` PascalCase, container `state` lowercase, health only in the Docker `status` string):
   - stack `deploying` or `created` → yellow; `running` and `unhealthy` → judged per service; `restarting` → red (Komodo sets it only when every container is in Docker's restart loop); every other state (`paused`, `stopped`, `dead`, `removing`, `down`, `unknown`) → red;
   - per service: `Running` with status containing `(unhealthy)` → red, `(health: starting)` → yellow, otherwise green; `Created` → yellow; `Exited` with `Exited (0)` → "completed", not counted; Swarm `Healthy` → green; `Restarting`, `Exited (n≠0)`, `Dead`, `Paused`, `Stopping`, `Removing`, `Unhealthy`, `Down`, `Unknown` → red;
   - the stack is the worst of its services; no countable service while running → red; "update available" shown, colour unchanged.
5. **Default wait for deploy/restart: 50 s** (`wait_seconds`, 5–600). The MCP TypeScript SDK's default request timeout is 60 s and most clients keep it; 50 s returns before it. On timeout the tool returns "still running, update id …".
6. **Komodo errors are HTTP 500 with `{error, trace}`** for "not found" and "no permission" alike (`mogh_error` 1.0.4 defaults to 500; `get_check_permissions` raises plain `anyhow`). The client classifies by message: `Did not find any Stack matching` / `does not have required permissions` → `KomodoErrorKind.NotFoundOrForbidden`; 401 → `Unauthorized`.
7. **A refused deploy** is answered by Komodo with an `Update` (200) whose task then fails with a log stage `Task Error` containing `does not have required permissions`: the tool reads that and says "your Komodo user lacks Execute on stack X".
8. **list_stacks** calls `ListStackServices` for each stack whose state is `running` or `unhealthy` (at most 4 at once), so "green" includes health.
9. **Audit** is a log category `Komogentic.Audit`, one line per tool call: user, credential kind and id, connection/key name, client, tool, stack, outcome.
10. **API keys whose Komodo key is rejected** become `dead` with reason `komodo_key_rejected`; connections become `needs_reconnect` with that reason and can be reconnected through consent.
11. **Traefik:** `compose.traefik.yaml` modelled on Kumbu²'s, optional.
12. **Web app without Tailwind and without openapi-fetch**: a few hand-written CSS rules and a 40-line `fetch` wrapper, fewer dependencies (all remaining ones are Kumbu²'s).

## Plan review amendments (binding; they override the task text where they differ)

A fresh reviewer read the spec, the brief and this plan. Its findings and what was done with them:

- **R1 — A stale-key 401 must not kill a reconnected connection.** `IssueCodeAsync` revokes the connection's earlier token family in its transaction (reason `reconnected`). `ICredentialHealth.KomodoKeyRejectedAsync` gets the rejected Komodo key and acts only if it is still the credential's current `komodoKey` (connections and API keys alike). Test: `ConnectionApiTests.Old_tokens_after_reconnect_do_not_kill_the_new_grant` (Task 8b).
- **R2 — Komodo rate-limits auth failures per IP, and it only sees the gateway's IP** (defaults 5 failures per 15 s, `bin/core/src/auth/mod.rs:69-88`). Add `KomodoErrorKind.RateLimited` (HTTP 429: "Komodo is refusing sign-ins for a moment after several failures; try again in a minute."). A 429 never marks a credential dead. Credentials already marked dead are refused by Komogentic without calling Komodo. `SignInLimiter` allows **3 attempts per minute per username and 5 per address**. The README documents Komodo's `KOMODO_AUTH_RATE_LIMIT_*` settings. Test: `KomodoClientTests.Rate_limited_is_its_own_kind` (Task 3), `SessionTests.Komodo_rate_limit_is_explained` (Task 4).
- **R3 — `list_stack_updates update_id` is tied to the stack.** Refused unless `update.target` is `{type: Stack, id: <resolved stack id>}`. Test: `StackToolsTests.Update_of_another_target_is_refused` (Task 6).
- **R4 — Service names are checked** against `^[A-Za-z0-9][A-Za-z0-9_.-]*$`, then against the stack's services from `ListStackServices`, before any logs, search, deploy or restart call. Test: `StackToolsTests.Unknown_or_malformed_service_is_refused` (Task 6).
- **R5 — Logs permission and Swarm.** A permission error from `GetStackLog`/`SearchStackLog` after a successful `GetStack` reads "your Komodo user lacks the Logs permission on stack X". For a Swarm stack (`swarm_id` not empty), the log tools need exactly one service and say so. Both go in the README. Tests: `StackToolsTests.Logs_without_logs_permission_say_so`, `Swarm_logs_need_one_service` (Task 6).
- **R6 — A code never exchanged.** Its Komodo key is queued in `pending_deletions` in the same transaction that stores the code, with `notBefore = code expiry`. `ExchangeCodeAsync` removes that row on success. `DrainAsync` deletes only rows whose `notBefore` has passed. The connection then shows `needs_reconnect` with reason `code_unused` when it has a key but no live tokens and was never exchanged. Test: `ConsentTests.Unexchanged_code_leaves_no_live_key` (Task 8b).
- **R7 — Token endpoint rate limits** (Kumbu²'s `OAuthLimits.TokenReserve/Failed/Release`, 20 failures per minute per client id and network) are part of Task 8a. Test: `TokenTests.Failed_token_requests_are_limited_per_client_and_network`. **Refresh-token lifetime:** until the connection expires, or without an expiry none (as in Kumbu²); there is no separate expiry.
- **R8 — Update shapes.** `ListUpdates` returns `{updates, next_page}` (100 per page, newest first). `UpdateListItem` has no `end_ts`, so `list_stack_updates` calls `GetUpdate` for each item shown (at most `limit`, 4 at once) to give the end time. Model and fake follow that.
- **R9 — One deadline per tool call.** Deploy and restart compute one deadline (`wait_seconds` from the start of the call). Every Komodo request in the call is cancelled at it, and the tool answers "still running" (if an update id is known) or "Komodo did not answer in time". Test: `StackToolsTests.Slow_komodo_does_not_exceed_the_wait` (Task 6).
- **R10 — Workflow fallback.** Not needed: the CI commit was pushed with `.github/workflows/ci.yml` and accepted.
- **R11 — Ordering and wording.** Task 0's MongoDB start and its package.json order are as executed (MongoDB started before Step 1; package.json written before the red web test). `Session_cookie_does_not_open_mcp` is part of Task 5 Step 1. **Task 8 is split into 8a** (OAuthTokens: code exchange, refresh, revoke, token rate limits; `/mcp/c/{id}` middleware; `/oauth/token` and `/oauth/revoke`) **and 8b** (consent API, connection API, `IssueCodeAsync`, reconnect, needs-reconnect states). Task 10's second mutation is: "show the API key's secret in the list after creation → 'shows a new key once' fails". This review and its folding-in are recorded here; the plan is committed after it.
- **R12 — The closed list is enforced by type.** `KomodoClient` has one private `SendAsync(KomodoCall call, KomodoAuth? auth, object parameters, CancellationToken)`. `KomodoCall` is a sealed class with a private constructor whose only instances are the static fields of `KomodoCalls`. Tests: `ClosedListTests.Calls_are_exactly_the_closed_list` (reflection over the `KomodoCall` fields), `Only_send_builds_requests` (reflection: `KomodoClient` has exactly one method taking a `KomodoCall`, and no other method references `HttpRequestMessage`), plus the source scan and the fake's `Violations`.
- **R13 — Trusted proxy.** Kept as in Kumbu² (any peer is trusted only when `Komogentic:Proxy:Trusted` is set, `ForwardLimit = 1`, the rightmost entry). The proxy network's addresses are assigned by Docker, so they can't be pinned. The README and `.env.example` say the setting is only for a proxy that is the only way in. This is the accepted limit of Kumbu²'s design (rule 2), recorded as a decision.
- **R14 — Smaller points.** A 401 on a JWT call ends the dashboard session ("Your Komodo sign-in has ended; sign in again."), it never marks a credential. The README says `Komodo:Url` over plain http only on an internal network. A connection's `lastUsedAt` is written at most once a minute, as an API key's.

## Review Focus

1. **A Komodo that is down or slow** during sign-in, consent or a tool call: the user/agent gets a clear "Komodo could not be reached" message, the request does not hang beyond `Komogentic:Komodo:TimeoutSeconds` (default 30 s), and nothing half-created is left without a pending deletion. Test: `KomodoClientTests.Unreachable_core_is_a_clear_error` and `ConsentTests.Allow_when_komodo_is_down_is_503_and_keeps_the_request` (Tasks 3, 8).
2. **A stack name with odd characters or an id instead of a name** (`app`, `my-app`, Mongo id): resolved through `GetStack`, the canonical name used afterwards. Test: `StackToolsTests.Stack_is_found_by_id_too` (Task 6).
3. **Two refreshes at once from the same client** (claude.ai retries): one rotation, both get a working pair inside the grace period. Test: `RefreshTests.Parallel_refreshes_get_the_same_pair` (Task 8).
4. **Huge logs**: a 5000-line tail must not exceed a sane tool result; the tool trims to the last 5000 lines and at most 200 000 characters, saying so. Test: `StackToolsTests.Logs_are_trimmed_with_a_note` (Task 6).
5. **The JWT expiring during a dashboard session** (Komodo `jwt_ttl` shorter than 12 h): the session ends at `exp`, the next `/api` call is 401 and the dashboard shows sign-in. Test: `SessionTests.Session_ends_with_the_jwt` (Task 4).
